# Oh, WAWD!

**What are we doing, and when can we do it?**

Oh, WAWD! is a shared planning space for product and engineering. Linear remains the source of projects, issues, and execution status. Oh, WAWD! connects that work to desired outcomes, delivery targets, dependencies, team capacity, and explicit scope tradeoffs.

The first product surface is the **Sequencing Board**: five parallel planning streams, a separate deferred shelf, a target-aware capacity forecast, and saved planning scenarios. The initial design is in [docs/product-design.md](docs/product-design.md), with exact forecast and scenario rules in [docs/scheduling-contract.md](docs/scheduling-contract.md).

## Run the private proof

This repository contains the three-slice private product proof: a single-owner React/Next.js app with read-only Linear import for one team, durable PostgreSQL storage, outcomes linked to imported projects, a five-stream sequencing board, and versioned decision scenarios. It creates one stable work package per project; linking a project to multiple outcomes does not create duplicate demand.

Requirements: Node.js 20.9 or newer and PostgreSQL 16 (or Docker Compose). The Compose file is development-only and starts a loopback-bound database with a readiness check. Create `.env.local` from `.env.example`, use `openssl rand -hex 32` for `SESSION_SECRET`, and use `openssl rand -base64 32` for the stable encryption key. Run `npm run set-owner-password` in a terminal; it prompts for the owner password without echoing it and saves a salted hash in `.env.local`. Any password characters work without quoting or escaping. Restart the server after changing these settings. Keep `.env.local` private and back up the encryption key along with the database; changing it makes the saved Linear key unreadable. Production requires `DATABASE_SSL=require` with a certificate trusted by the Node runtime. Size `DATABASE_POOL_MAX` so the total across all replicas remains below the database connection limit. Set `TRUST_PROXY=true` only behind a proxy that strips client-supplied forwarding headers; production should also enforce a shared sign-in rate limit at that proxy.

```sh
npm install
npm run set-owner-password
npm run db:migrate
npm run dev
```

Open `http://localhost:3000`, sign in, enter a Linear API key, check access, choose one team, preview its projects, and import. The preview includes all project states. You can create an outcome before importing, then link each imported project as minimum-required or optional. Search and status-filter the imported list, or hide irrelevant projects from planning lists; hiding is reversible and preserves existing outcome links. Completed projects remain available. Subsequent imports for the same team can use the saved server-side key, deduplicate projects, issues, and cycles by Linear ID, preserve outcome links and local visibility choices, and flag projects absent from the latest import for review. A different team requires a new workspace; this proof does not merge teams.

The board places newly imported selected packages on **Needs assignment**. It reads the connected team's cycle names, dates, timezone, and cadence from Linear; there is no local cycle-date editor. Choose a provisional baseline with a reason (or use the median of at least three comparable completed Linear cycles), set reserve, and allocate at most 100% across the active streams. The visible calendar lets you select a date in one or several upcoming Linear cycles, then apply availability or reserve exceptions to those cycle IDs. You can refresh cycles with the saved Linear key without reimporting every project. The current partial cycle is context only. If Linear has not created a future cycle, the forecast stops at the last imported cycle instead of inventing dates; increase the team's upcoming cycle count in Linear and refresh to extend the calendar.

Assign packages, prioritize them, choose optional preferred and hard earliest Linear cycles, and add local dependencies. Linear project dependencies are imported as read-only constraints; a waiver needs a visible reason. **Deferred** packages consume no future capacity. Pausing in-progress Linear work here is a planning assumption and must be carried out separately in Linear. Minimum-required outcome links determine the first delivery cycle, including dependency closure; optional links affect that date only when they block required work. The board shows unknown estimates, provisional allowances, cross-team exclusions, target gaps, and a cycle-by-cycle capacity explanation. Existing relative cycle exceptions and start preferences are mapped to imported Linear cycle IDs when possible; settings beyond the imported calendar are kept for review.

The key is sent to the Node server over the app connection and stored only as AES-256-GCM ciphertext in PostgreSQL. Use HTTPS if accessing the app outside localhost, and keep the proof behind private network access. The app never writes to Linear. It uses the [Linear TypeScript SDK](https://linear.app/developers/sdk) for paginated reads; the SDK rejects GraphQL responses containing errors, including partial responses. There is one owner password and no invited users or public sharing.

Use Decision scenarios to save the current board as a named draft. Draft saves use optimistic versions, source refreshes mark existing drafts stale, and rebasing records the source-driven forecast delta. Load a draft to restore its planning controls, publish a reviewed draft with an author and rationale, designate a published revision as the baseline, and compare drafts or revisions side by side. Published revisions contain frozen source and forecast snapshots and are not changed by later imports.

Stream management can add zero-allocation streams, reorder active lanes, and retire a stream through a forecast preview that migrates every selected or deferred package. Retirement returns allocation to headroom and records an audit event. Published scenario revisions remain frozen; other drafts that reference a retired stream are blocked from loading or publishing until the stable stream ID is restored or the plan is recreated from the current board.

Run `npm test` for import persistence, forecast contract, and scenario lifecycle examples; run `npm run typecheck` for TypeScript and `npm run build` for a production build. Run `npm run db:migrate` once during each deployment, before starting new application instances. Migrations are versioned, transactional, and protected by a PostgreSQL advisory lock; the application verifies the complete migration ledger but never performs DDL at request time. `npm run start` serves the built app. `/api/health/live` is process liveness; `/api/health/ready` verifies the required schema version and database connectivity. The Dockerfile's default target is a minimal non-root standalone application image; build its `migrator` target as the pre-rollout migration job. Database backups, encrypted retention, restore drills, and deployment rollback remain operator responsibilities. Because application versions require their exact migration ledger, rollbacks must restore the matching database backup until migrations are explicitly designed as backward-compatible expand/contract changes.

Migration **6** adds the [outcome-first Board data foundation](docs/roadmap-migration.md); migration **7** activates the owner-safe [roadmap mutation contracts](docs/roadmap-mutations.md), conservative conversion and excluded-candidate defaults. Activated reads and publication now use [v5 outcome-priority scheduling](docs/scheduling-contract.md) with [scenario conversion and frozen-history compatibility](docs/scenario-v5-compatibility.md). The active OpenSpec change tracks the remaining Board and lifecycle controls.

The [outcome completion service](docs/outcome-lifecycle.md) now provides current-evidence readiness, versioned complete/reopen persistence and sticky review/history. It adds no migration beyond the existing lifecycle storage. Visible sidebar completion controls follow in their dependent task.

Public sharing, invited roles, Linear project creation, multi-team forecasting, and project decomposition remain beyond the private proof.
