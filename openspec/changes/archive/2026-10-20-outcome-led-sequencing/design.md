# Design

## Context
There is one work package per imported project. Its scalar stream and saved sequence feed the dependency-aware cycle scheduler. Outcome links are many-to-many, but outcomes have no stream placement or capacity owner. Existing uncommitted cycle-calendar work must be preserved.

## Goals / Non-Goals
Goals: outcome-first rows, exclusive accountable points, explicit cross-stream references, dependency-honest blocks, durable scenario inputs, accessible project inspection.
Non-goals: splitting project estimates across outcomes, changing scheduling granularity, adding mock-up-only engineering-required flags, or replacing Linear as execution authority.

## Decisions
1. **One stream per outcome; many linked projects.** Add nullable `outcome.stream_id`. Shared projects connect outcomes in different streams without cloning work packages. A many-stream outcome would introduce ambiguous row ownership without satisfying an additional requested use case.
2. **One nullable capacity outcome per work package.** Add `capacity_outcome_id` with a composite foreign key to the existing outcome/project link. Link removal clears this value, retaining the project's existing stream and charge under an unallocated-outcome bucket. A link edit upserts retained links instead of deleting/recreating all links. This avoids clearing valid owners on unrelated edits.
3. **The work package remains the only capacity charge.** Outcome counted totals include selected packages owned here; shared contributions show zero points here. Unowned selected work appears in an explicit “Other selected work” row in its actual stream, even when it also has mirrored outcome appearances. Stream/portfolio totals never sum mirrored blocks. Required outcomes still depend on the actual project's finish, irrespective of who pays; optional links remain visible but do not gate delivery.
4. **Explicit ownership transfer moves the existing queue entry atomically.** Validate the linked outcome and active assigned stream, require the board sequence token, use dependency-safe placement, then set ownership. A separate ownership token covers links, outcomes, and ownership so stale browser selections are rejected too. Assigning an outcome to a stream moves its already-owned projects and claims selected ownerless linked projects, but does not steal another outcome's projects or select deferred projects. Moving a project independently to another stream, Needs assignment, or Deferred clears incompatible ownership; moving within its owning stream retains it. Moving an outcome to Needs assignment clears its projects' owners without silently moving or deferring their work. Stream retirement unassigns outcomes and clears incompatible project ownership.
5. **Legacy migration is deterministic and conservative.** For each outcome infer the stream with most selected linked projects, breaking ties by stream position/ID. For each selected package choose the earliest-created linked outcome in its actual stream (ID tie-break). Preserve every existing project stream, sequence, selection, estimate, and published JSON. Adapt missing snapshot fields with the same rules when loading older drafts; explicit nulls remain null. Calculation v3 is retained because the math is unchanged. Scenario dirty detection, comparison, activation and retired-stream reconciliation include both new fields.
6. **One outcome row, collision-free project sublanes.** Preserve the month/week header and holiday/calendar bands. Place solid owned blocks in the upper portion and outlined shared blocks below with “Shared · 0 pts here” and owning location. Pack overlapping cycle spans into separate sublanes, retaining WIP overlap rather than inventing serial timing. Unscheduled/deferred/complete projects remain clickable chips with reasons. References always use the owning package's forecast. Dependencies appear by compact project code and in full in the drawer; clickable predecessor/successor navigation provides cross-stream tracing without a dense overlay of arrows.
7. **Short codes and one modal sidebar.** Derive mnemonic initials with deterministic collision suffixes across the workspace; show full names in tooltips, accessible names, a row project key, and the drawer. Native dialog supplies focus containment/Escape; restore focus to the opening block or a safe stream heading if that block disappears after a transfer. The drawer shows imported description/status/link, estimate basis, unestimated issues, scope readiness, all linked outcomes, counted location, and dependency navigation. Reuse existing placement and scope controls without mounting duplicate board-card IDs.

## Risks / Trade-offs
- A cross-stream transfer can change downstream dates → retain dependency validation and reload all forecast rows after a transaction.
- A shared-only row can look empty → show a dedicated outlined reference band and explicit zero-count annotation.
- Initial inference can choose an unexpected owner → preserve the actual stream, surface the chosen owner, and provide immediate reassignment.
- Owner deletion or stream retirement can strand accounting → clear the outcome owner and show the original charge in Other selected work.
- Cycle-sized blocks overlap even for short sequential work → pack vertically using forecast dates, never compress time to imitate the mock-up.

## Pre-implementation double-check
Reviewed same-stream sharing, cross-stream sharing, optional links, multiple owners attempted, stale tabs, dependency rejection/rollback, WIP overlap, beyond-horizon work, empty outcomes, hidden work, deferral, unlinking/deletion, stream retirement, and scenario save/load/compare. All use one authoritative package and one capacity charge. Neither linking nor display is a scheduling dependency; existing explicit edges alone constrain project starts. Ownership transfer does not remove any outcome links.

## Migration Plan
Add a versioned additive migration and backfill existing live data once. Exercise it on an in-memory PostgreSQL database. Operators run the normal migration command before starting the updated app. Rollback can retain additive columns with the previous app; existing project scheduling fields remain compatible. Do not alter published scenario revisions.
